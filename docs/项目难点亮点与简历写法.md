# DeepSearch 项目：技术难点 · 项目亮点 · 简历写法

---

## 0. 项目陈述

> DeepSearch 是一个基于 LangGraph + DeepAgents 的企业级多智能体深度搜索平台。我做了三件事：  
> **一**，用「主智能体 + 3 个专家子智能体」的主从编排，把互联网（Tavily）、结构化业务数据（MySQL）、私有知识库（RAGFlow）三类异构数据源统一到一个自然语言入口，一次提问即可完成「检索 → 融合 → 生成 Markdown/PDF 报告」的闭环；  
> **二**，基于 `astream` 流式事件 + 工具内部埋点的**双通道可观测方案**，把模型决策、工具调用、子智能体委派全程通过 WebSocket 推到前端「思维过程」面板，让黑盒 Agent 的执行链路完全可见；  
> **三**，用 `ContextVar` + 会话沙箱目录 + 路径解析器解决了异步并发下的**会话串台**和**大模型伪造路径**这两个工程硬问题，并给文件下载接口做了 `Path.resolve() + is_relative_to()` 的越权校验。

## 2. 真实执行链路（面试画图就画这个）

```
用户提问
  │
  ├─ POST /api/task ──► asyncio.create_task(run_deep_agent) ──► 立即返回 {status:"started", thread_id}
  │                                                              （HTTP 不阻塞，进度走 WS）
  ▼
run_deep_agent(query, session_id)
  ├─ 建目录 output/session_{id}；把 updated/session_{id} 的上传文件 copy2 进来
  ├─ set_session_context() / set_thread_context()   ← ContextVar 会话隔离
  ├─ monitor.report_session_dir()                   ← WS: session_created
  │
  ▼
async for chunk in main_agent.astream(...)          ← 流式，逐节点
  ├─ node == "model" & tool_calls 里有 task         ← 判定为「委派子智能体」
  │     └─ monitor.report_assistant()               ← WS: assistant_call
  ├─ node == "model" & 有 content 无 tool_calls     ← 最终答案
  │     └─ monitor.report_task_result()             ← WS: task_result
  └─ node == "tools"                                ← 不在这里埋点（工具内部已埋）
        └─ 各 @tool 内部 monitor.report_tool()      ← WS: tool_start
  │
  ▼
finally: reset_session_context()                    ← 必须 reset，防上下文污染
```

## 3. 八大技术难点

### 难点 1：异步并发下的会话串台 —— 为什么全局变量和 threading.local 都不行

**现象**：多个用户同时提问时，A 用户生成的文件会写进 B 用户目录，WS 消息也会发给错误的人。

**根因分析**：

- FastAPI 的多个请求跑在**同一个线程**的不同协程里，全局变量会被并发覆盖；
- `threading.local` 是**线程级**隔离（只能同步任务），单线程多协程场景下完全失效；
- 结论：必须用**协程级**变量 → Python 3.7+ 的 `ContextVar `(thread_id / session_id 是一个东西，是前端随机生成的 id，作为当前会话 id 和记忆键，如果前端不传则后端随机生成一个 id 作为会话 id)。

**方案**（`api/context.py`）：

```python
_session_dir_ctx: ContextVar[Optional[str]] = ContextVar("session_dir", default=None)
_thread_id_ctx:  ContextVar[Optional[str]] = ContextVar("thread_id", default=None)

# set 返回 Token，finally 里用 Token 精确 reset（而不是 set(None)）
# 把当前任务的所有信息约束到 ContextVar 中
token = set_session_context(session_dir_str)
try:    ...
finally: reset_session_context(session_dir_token, session_id_token)
```

**关键细节**：`asyncio.create_task` 会**复制**当前 context 作为 ContextVar（单线程事件循环，一个 CPU 跑全部请求，在 await 点协程主动让出 CPU，事件循环去跑另一个 Task → 看起来"同时"处理 A/B/C 三个任务，其实单线程快速切换；三个 Task 同处一个线程，但各自的 ContextVar 互不干扰 → A 调工具时 get() 到的永远是 A 的 thread_id），所以每个 `run_deep_agent` 任务天然拥有独立副本；但同一任务内如果 `set` 后不 `reset`，会污染后续复用的 task / 线程池上下文 —— 所以 `finally` 里的 `reset(token)` 是必需项。

工具函数在任意深度调用（`read_file_content` → `resolve_path` → 写盘）都能通过 `get_session_context()` 拿到当前会话目录，**不用把 session_dir 层层透传**，签名保持干净。

### 难点 2：跨线程 / 跨事件循环的 WebSocket 推送

**现象**：工具埋点有时推不到前端，甚至抛 `coroutine was never awaited` / `attached to a different loop`。

**根因**：LangChain 的同步工具（`mysql.connector`、`requests`、`win32com`）会被丢到**线程池**里执行，此时 `asyncio.get_running_loop()` 拿到的是另一个 loop，甚至是 `RuntimeError`；而 `WebSocket.send_json` 必须在 FastAPI 主事件循环里执行。

**方案**（`api/monitor.py`）：**双路径投递 + 启动时绑定 loop**

```python
# startup 阶段把主 loop 绑到 manager 上（关键：不能在模块导入时取 loop）
@app.on_event("startup")
async def startup_event():
    manager.set_loop(asyncio.get_running_loop())

# 埋点发送时先判断自己在哪个 loop
try:    current_loop = asyncio.get_running_loop()
except RuntimeError: current_loop = None

if current_loop is manager_loop:
    current_loop.create_task(send(...))          # 同 loop：零拷贝、最轻
else:
    asyncio.run_coroutine_threadsafe(send(...),  # 跨线程：线程安全
                                    manager_loop)
```

**另外做了降级设计**：WS 不可用时，依次降级到 `builtins.runtime.stream_writer`（脚本模式）→ `print` 控制台，保证「脚本单跑」和「服务模式」共用同一套埋点代码。

**为什么这是难点**：大多数人踩坑后会用一个全局 `asyncio.Queue` 硬扛，但队列消费端仍需在正确 loop 上 await；这里直接用 `run_coroutine_threadsafe` 精确投递到目标 loop，是标准解法。

### 难点 3：从 `astream` chunk 里捞出「子智能体委派」事件

**现象**：只知道 Agent 在跑，但看不到它把任务分给了哪个助手 —— 前端「思维过程」一片空白。

**根因**：DeepAgents 的子智能体委派**不是独立节点**，而是主智能体调用了一个叫 `task` 的特殊工具。chunk 结构按节点返回：

- `node == "model"` + `tool_calls` 里有 `{"name": "task", "args": {"subagent_type", "description"}}` → 这才是委派；
- `node == "model"` + 有 `content` 无 `tool_calls` → 最终答案；
- `node == "tools"` → 工具执行结果（**这里不要埋点，会造成重复推送**）。

**方案**（`agent/main_agent.py`）：解析 chunk 时按 `node_name` 分支 + 按 `tool_call.name` 二次判别：

```python
for node_name, state in chunk.items():
    if not state or "messages" not in state: continue
    last_msg = state["messages"][-1]
    if node_name == "model":
        if last_msg.tool_calls:
            for tc in last_msg.tool_calls:
                if tc["name"] == "task":                      # 委派信号
                    monitor.report_assistant(tc["args"]["subagent_type"],
                                             {"description": tc["args"]["description"]})
        elif last_msg.content:
            monitor.report_task_result(last_msg.content)       # 终态
```

**这构成了「双通道埋点」架构**：

| 通道    | 位置                       | 负责          | 为什么不能合并                 |
| ----- | ------------------------ | ----------- | ----------------------- |
| 编排层解析 | `main_agent.py` 解析 chunk | 子智能体委派、最终答案 | 工具内部拿不到「被谁委派」           |
| 工具层埋点 | 每个 `@tool` 函数首行          | 工具名 + 入参    | chunk 里工具结果已被合并，拿不到精确入参 |

### 难点 4：大模型伪造路径 —— LLM 会写出 `/workspace/xxx.md`、`session_123/session_123/xxx.md`

**现象**：生成的报告时而消失、时而落到了奇怪目录，PDF 报「文件不存在」。

**根因**（三类脏输入，实测都出现过）：

1. **虚拟路径幻觉**：模型按训练语料习惯输出 `/workspace/report.md`、`/mnt/data/a.md`；
2. **路径重复拼接**：提示词给了相对目录 `output/session_abc`，模型又在前面拼一次 → `session_abc/session_abc/report.md`；
3. **越权绝对路径**：模型直接写 `D:/OtherDir/file.md`。

**方案**（`utils/path_utils.py`）：

```
① 剥离虚拟前缀 /workspace | /mnt/data | /home/user
② 命中 "updated/" → 重定向到上传目录（LLM 上下文里这两个目录是混的）
③ Windows 特例：'/' 开头但无盘符 → 视为相对路径（不是真绝对路径）
④ 检测 parts[i] == session_name and parts[i+1] == session_name → 折叠嵌套
⑤ 最终一律收敛到 session_dir 下
```

**配套的三层防护**：

| 层    | 手段                                                   | 位置                                             |
| ---- | ---------------------------------------------------- | ---------------------------------------------- |
| 提示词层 | 明确「工作目录 + 只用相对路径 + 禁止绝对路径」                           | `main_agent.py` 的 `path_instruction`           |
| 代码层  | `resolve_path()` 清洗 → 所有文件工具统一入口                     | `tools/*.py`                                   |
| 接口层  | `Path.resolve()` + `is_relative_to(output_dir)` 双重校验 | `api/server.py` 的 `/api/files`、`/api/download` |

这是「LLM 输出不可信」的典型工程化落地 —— 安全边界不能靠提示词，必须在代码层做**白名单收敛**。

### 难点 5：多智能体的「上下文污染」与「工具越权」治理

**现象**：早期主智能体既查数据又写文件，导致两个问题：① 主 Agent 上下文被海量检索结果塞爆；② 模型在拿到信息前就调用 `generate_markdown`，用「等待子任务完成」之类的占位符糊出一篇空报告。

**方案**：

1. **工具权限分层**（`main_agent.py`）：
   - 主智能体**只**持文件类工具：`generate_markdown`、`convert_md_to_pdf`、`read_file_content`；
   - 子智能体**只**持数据类工具，**不持有任何文件写入能力** → 从工具层面根除「子智能体乱写文件」。
2. **职责边界写进 prompt**（`prompt/prompts.yml`）：
   - 「文件生成由你自己完成，**不需要**把文件地址告诉子智能体」；
   - 「**绝不允许**在获取信息之前调用 `generate_markdown`」；
   - 「严禁使用『等待子任务完成』之类的占位符生成文件」；
   - 「如果你需要先搜索再生成，请**分两步**，不要在同一个 Tool Call 列表里同时做这两件事」。
3. **行为量化约束**：网络搜索助手「至少 3 个角度、最多 5 次」；RAGFlow 助手「至少提问 3 个不同问题、保留原始信息不概括」；报告「不少于 1000 字」。

**关键认知**：多智能体的第一原则不是「拆得越细越好」，而是**用工具权限切出物理边界，用提示词切出语义边界**。第 4 条「不要在同一 Tool Call 列表里并行做两件事」这一句，是踩了坑之后加进去的 —— 因为模型倾向于一次性规划完所有调用，导致生成工具拿不到检索结果。

### 难点 6：三类异构数据源 → 统一成 LLM 可读文本

| 数据源     | 原始返回                                         | 工程处理                                                       | 为什么这么做                                             |
| ------- | -------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------- |
| Tavily  | 嵌套 JSON（含 raw_content 可能几万字）                 | `include_raw_content` 参数开关 + `topic` 分类 + `max_results` 限流 | 直接塞原文会瞬间打爆上下文                                      |
| MySQL   | 游标元组 `[(1,'张三'),...]` + `cursor.description` | 转 **CSV 文本**（列头 + 行），`get_table_data` 硬限 100 行             | CSV 是 LLM 最省 token 又最能理解表格的格式；比分 JSON 省 30%+ token |
| RAGFlow | SDK 流式 `part.content`                        | 「建会话 → 提问 → 立即删会话」一次性模式                                    | 避免临时会话堆积；流式只取最后一段完整 content                        |

**RAGFlow 一次性会话模式**（`tools/ragflow_tools.py`）：

```python
session = use_chat.create_session(name="temp_session_ask")
for part in session.ask(question=question, stream=True):
    result = part.content            # 流式拼到最后一帧
use_chat.delete_sessions(ids=[session.id])   # 用完即删，不留垃圾会话
```

**细节**：因为 RAGFlow 的话题必须匹配助手描述，工具描述里强制「先 `get_assistant_list` 拿到助手名和知识库范围，再提问」，避免模型对着「空调安装助手」问药品销售。

### 难点 7：无 LaTeX / WeasyPrint 依赖下的 PDF 生成

**约束**：项目跑在 Windows 内网环境，不想引入 wkhtmltopdf / weasyprint 这类重量级二进制依赖。

**方案**（`utils/word_converter.py`）：`Markdown → HTML(带内联 CSS) → Word COM → PDF`

```python
pythoncom.CoInitialize()                     # COM 必须初始化（多线程场景尤其）
word_app = win32com.client.Dispatch('Word.Application')
word_app.Visible = False; word_app.DisplayAlerts = False
doc = word_app.Documents.Open(str(html_path))
doc.SaveAs(str(pdf_path), FileFormat=17)     # wdFormatPDF = 17
```


**踩过的坑（都能展开讲）**：

- 必须 `CoInitialize` / `CoUninitialize` 成对出现，否则线程池里调用会挂；
- `Visible=False` + `DisplayAlerts=False`，否则服务器上会弹出 Word 窗口卡死流程；
- 临时 HTML 与 Word 进程**必须在 `finally` 里清理**，否则残留 `WINWORD.EXE` 进程；
- 表格/代码块样式靠 HTML 内联 CSS（`border-collapse`、`white-space`）承载，Word 才能正确解析；
- 真实局限：**Windows + 已装 MS Word 才可用**，Linux 需换 LibreOffice headless（已写进已知限制）。

### 难点 8：HTTP 立即返回 + 长任务异步执行

**问题**：一次深度搜索可能跑 1–3 分钟，同步 HTTP 必然超时。

**方案**：

```python
@app.post("/api/task")
async def run_task(request: TaskRequest):
    thread_id = request.thread_id or str(uuid.uuid4())
    asyncio.create_task(run_deep_agent(request.query, thread_id))  # 后台跑
    return {"status": "started", "thread_id": thread_id}           # 立即返回
```

**配套的三件事（缺一不可）**：

1. 任务体必须 `try/except` 兜底，异常通过 `monitor._emit("error", ...)` 推前端，否则异常被 `create_task` 静默吞掉；
2. `finally` 里 `reset` ContextVar；
3. 前端以 `thread_id` 订阅 WS，生命周期与任务解耦（刷新页面用 `crypto.randomUUID()` 保持会话）。

| # | 亮点                       | 支撑事实（可验证）                                                                   |

**工程规范亮点**：

- 每个 `@tool` 三要素齐备：**类型注解（`Annotated`）+ 中文 docstring（LLM 靠它决定调用）+ 埋点**；
- 工具文件自带 `if __name__ == "__main__"` 单测入口，可脱离 Agent 独立验证；
- 数据库连接统一 `with connect(...) as conn` 上下文管理，异常一律转**可读文本**返回而非抛出（Agent 拿到错误能自我修正，不会中断任务）。

## 5. 简历写法

### 5.1 版本 A：AI 应用开发岗

> **DeepSearch ｜ 企业级多智能体深度搜索与报告生成平台** ｜ 独立开发 ｜ `Python / LangGraph / DeepAgents / FastAPI / Vue3`
>
> - 基于 **DeepAgents（LangGraph Runtime）** 搭建「1 主 + 3 子」主从编排：主智能体负责规划与文档产出，网络搜索 / MySQL 查询 / RAGFlow 知识库三个专家子智能体负责取数，打通「检索 → 融合 → 生成 Markdown/PDF 报告」全链路，单一自然语言入口覆盖互联网、结构化业务数据、私有知识库三类异构数据源。
> - 设计**双通道可观测方案**：编排层解析 `astream` chunk 识别工具调用与 `task` 委派信号，工具层在 `@tool` 内部埋点上报入参，经 WebSocket 五类事件将模型决策链路实时推送至前端「思维过程」面板，使 Agent 执行过程从黑盒变为可追溯。
> - 用 **`ContextVar`（协程级变量）+ Token reset + 会话沙箱目录**解决 FastAPI 异步并发下的会话串台问题（对比全局变量与 `threading.local` 在单线程多协程场景失效），多会话并发下文件与消息零串台。
> - 针对大模型生成路径不可信（虚拟路径幻觉、目录重复拼接、越权绝对路径），实现统一路径解析器覆盖 12 类输入场景，并在文件下载/列表接口叠加 `Path.resolve() + is_relative_to()` 越权校验，杜绝目录遍历。
> - 通过**工具权限分层 + 提示词强约束**治理多智能体上下文污染：主 Agent 独占文件写入能力、子 Agent 只读数据源，并以「先取数后生成、禁止同一 Tool Call 列表并行」的硬性规则消除模型使用占位符糊报告的问题。

### 5.2 版本 B：全栈 / 后端岗

> **DeepSearch ｜ 多智能体搜索平台（FastAPI + Vue3）** ｜ 独立开发
>
> - 后端基于 **FastAPI** 实现 REST + WebSocket 双通道：任务接口 `asyncio.create_task` 异步派发后立即返回 `thread_id`，长任务进度经 WS 定向推送，解决分钟级 Agent 任务的 HTTP 超时问题。
> - 解决**跨线程跨事件循环的消息投递**难题：工具（MySQL/COM/Tavily）运行在线程池，埋点统一走「同 loop → `create_task`、跨线程 → `run_coroutine_threadsafe`」双路径，并在 `startup` 阶段显式绑定主 loop，避免 `coroutine never awaited` 与跨 loop 报错；WS 不可用时自动降级为脚本流式输出与控制台日志。
> - 设计**会话级文件沙箱**：`output/session_{thread_id}` 独立工作目录 + `ContextVar` 上下文注入，工具在任意调用深度可无参获取当前会话目录，`finally` 中 Token reset 防止上下文污染与内存泄漏。
> - 前端 Vue3 + TS + Vite 单页应用：WebSocket 断线 3 秒自动重连、事件驱动渲染工具调用日志与文件卡片、`marked` 实时渲染 Markdown、内嵌会话文件浏览器（列表 / 预览 / 下载）。

### 5.3 版本 C：前端转 AI 岗

> - 独立完成**前端 + Agent 后端**全栈开发（Vue3/TS + FastAPI/LangGraph），把「流式事件驱动」这一前端熟悉的模式复用到 LLM 应用层：服务端定义 5 类语义事件（`session_created` / `tool_start` / `assistant_call` / `task_result` / `error`），前端按 `event` 做状态机渲染，实现 Agent 思考过程的实时可视化。
> - 主导工程化落地：统一工具开发范式（类型注解 + docstring + 埋点三要素）、提示词外置 YAML 配置化、工具文件内置 `__main__` 冒烟测试，使新增一个子智能体从「改 3 处代码 + 1 份配置」收敛为可复制的标准动作。

## 6. 高频追问 12 问 + 答题提纲

| #  | 问题                                | 答题要点                                                                                                         |
| -- | --------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1  | 为什么用 DeepAgents 而不是自己写 LangGraph？ | 它内置 `write_todos` 规划器、`task` 子智能体调度、文件系统后端，省掉 60% 编排样板；LangGraph 我只用来兜底自定义节点（`CompiledSubAgent` 方式已验证兼容）     |
| 2  | 子智能体是怎么被调用的？                      | 主 Agent 发起一个 `name="task"` 的特殊 tool_call，`subagent_type` 决定目标，`description` 下发任务；`description` 写得准不准直接决定路由质量 |
| 3  | 为什么不把所有工具都给主 Agent？               | 上下文污染 + 权限失控。检索结果几万字会把主 Agent 上下文塞爆；且子 Agent 一旦有写文件能力就会乱建文件                                                  |
| 4  | 怎么保证多个用户同时用不串数据？                  | `ContextVar` 协程级隔离（不是全局、不是 thread-local）+ 每会话独立沙箱目录 + Token 精确 reset                                         |
| 5  | WebSocket 推送为什么会失败？你怎么定位的？        | 工具跑在线程池 → 跨 loop；解法是 startup 绑 loop + `run_coroutine_threadsafe`；日志里能看到 `对比是不是同一个event_loop` 的判定             |

| 7  | PDF 为什么不用 WeasyPrint / Puppeteer？ | 内网 Windows 环境不想引二进制依赖；Word COM 排版（表格、代码块）效果最接近办公场景；代价是平台绑定，Linux 会换 LibreOffice headless                     |
| 8  | 会话记忆怎么做的？重启会丢吗？                   | `InMemorySaver` + `thread_id` 绑定，重启即丢、多 worker 不共享 —— 这是我的**已知限制**，生产会换 Redis/Postgres checkpointer          |
| 9  | 如果让你优化性能，先动哪里？                    | ① 检索结果做摘要压缩再进上下文；② 跨源并行（目前四类响应式排序成串行）；③ 换持久化 checkpointer 解锁多 worker；④ 文件列表 `rglob` 加深度限制                    |
| 10 | 这个项目最难的点是什么？                      | 答「异步并发下的上下文隔离 + 跨 loop 消息投递」—— 因为它是**静默失败**的：不报错，只是数据错乱，排查成本远高于语法错误                                          |
| 11 | 你怎么测试的？                           | 工具层 `__main__` 单测（脱离 Agent 跑真库/真接口）+ 端到端手工用例（纯查询 / 带文件 / 生成 PDF 三类）+ 路径解析 12 场景对照表                           |

## 8. 这个项目有什么业务价值

> 它解决的是企业里最常见的问题：**业务数据在 MySQL 里、制度文档在知识库里、行业动态在互联网上**。分析师要写一份研报，得分别找人导数据、翻文档、搜网页，再手工拼 Word。  
> 这个平台把这三步收敛成一句话（比如「分析某药品近半年华东区销售趋势并输出报告」），由主智能体自动并行调度三类数据源，最后直接产出可下载的报告。**价值不在『能搜』，而在『搜完能出一份能交出去的文档』** —— 这也是我把文件生成能力从子智能体手里收回、只留给主智能体的原因：责任边界必须单一。
